# consolidate-learnings スキル

`LEARNINGS.md` を開き、全項目を見直す。

1. 古い項目を削除する
2. 重複をマージする
3. パターンを見つけ、統合した原則を `Consolidated Principles` に書く

削除・マージした項目は、必ず変更前後がわかる形で報告する。黙って消さない。

## 対象ファイル

- プロジェクトのルート(`git rev-parse --show-toplevel`。git 管理外ならカレントディレクトリ)直下の `LEARNINGS.md`
- 無ければ統合するものが無いので、「`LEARNINGS.md` がありません。先に `/update-learnings` で学びを記録してください」と伝えて終わる

## 手順

### 1. 現状を読む

`LEARNINGS.md` を全文読み、統合前の項目数を数えておく(報告で前後を比べるため)。

```bash
awk '/^## Consolidated Principles/{skip=1; next} /^## /{insec=1; skip=0; next} insec && !skip && /^- /{n++} END{print n+0}' LEARNINGS.md
```

古さの判断に必要なら、`CLAUDE.md`・該当するコード・`git log` を確認する。

### 2. 古い項目を削除する

次のどれかに当てはまる項目を削除候補にする。

- 前提が変わり、もう当てはまらない(仕様・構成・運用が変わった)
- `CLAUDE.md` に同じ内容がルールとして取り込まれ、二重になっている
- 解決済みの `Open Questions`(答えが出たら、その答えを該当セクションの項目に書き換える)

迷う項目は削除せず残し、報告で「判断を保留した項目」として挙げる。

### 3. 重複をマージする

同じことを別の言い回しで書いている項目を 1 つにまとめる。

- 具体例・Issue/PR 番号(`(#12)` など)は落とさず、まとめた項目に寄せる
- まとめた項目は元の項目のうち最も適切なセクションに置く

### 4. 原則を抽出する

複数の項目(目安 2〜3 件以上)に共通するパターンを見つけ、1 行の原則として `Consolidated Principles` に書く。

- 書き方: `- <原則>(根拠: <元の項目の要約や Issue 番号>)`
- 原則に吸収された元の項目は、具体例として価値があれば残し、原則の言い換えにすぎなければ削除する
- 既存の原則と同じなら新しく足さず、根拠を補強する。既存の原則が古くなっていれば手順 2 と同じ基準で見直す
- 共通パターンが見つからなければ、無理に作らない

### 5. 最終統合日を更新する

`Consolidated Principles` 見出しの直下に、今日の日付で次の 1 行を置く(既にあれば日付だけ書き換える)。`/update-learnings` がリマインドの判定に使う。

```markdown
## Consolidated Principles

最終統合: YYYY-MM-DD
```

セクションに `(まだなし。…)` のようなプレースホルダーしか無く、原則も書かなかった場合は、プレースホルダーをこの 1 行で置き換える。

### 6. 報告する

次の順で報告する。

- 項目数: 統合前 → 統合後
- **削除した項目**: 元の文面と削除理由
- **マージした項目**: 元の項目(複数)→ まとめた後の文面
- **追加・補強した原則**: 原則の文面と根拠
- 判断を保留した項目(あれば)
- 最後に「この変更は Issue → ブランチ → PR の流れでコミットしてください」と案内する

変更が 1 件も無ければ、最終統合日だけを更新し、「統合する項目はありませんでした」と伝える。

## やらないこと

- 新しい学びを追記しない(セッションのふりかえりは `update-learnings` の担当)
- `CLAUDE.md` や自動メモリ(`~/.claude/memory/`)は書き換えない。`CLAUDE.md` に昇格させたほうがよい原則があれば、報告で提案するだけにする
- コミットしない。差分をレビューできるよう、ユーザーに頼まれたときだけ行う
